## ShiftLefter Intro

ShiftLefter is a Gherkin/BDD test framework in Clojure: a Gherkin parser,
formatter, and runner (Gherkin-compliant — 50/50 official Cucumber test files), plus a
typed Subject–Verb–Object vocabulary that validates steps before any browser
or SMS run. There is one mode: ShiftLefter parses all Gherkin and executes
only typed steps — a suite whose steps bind to nothing is a planning result
(exit 2), not a way of running. It
drives real browser sessions (one per actor) and other interfaces from plain
feature files, and it is built for agents to author and repair behavior against
durable project vocabulary rather than one-shot generated scripts.

You are reading the agent surface. Two commands orient you: `sl orient` reports
this project's resolved context and what is wrong with the project itself
(config, glossaries, steps — not your features; `sl run --dry-run` checks
those), and `sl agent-doc --list` names the doctrine topics below.

To judge whether ShiftLefter is a fit for a particular project — "would this work
for us here?" — read `docs/FIT.md`, the practical fit check. Hand it to the user's
agent alongside their repo/URL; it carries an explicit fit checklist and the
honest capability boundaries.

## Bring Existing Gherkin

ShiftLefter parses all Gherkin; the only thing it refuses to run is an untyped
step. This page is what that means for a Cucumber suite you already have: what
works the moment you point `sl` at it, what `sl run` tells you, and what
"shifting" the suite actually involves.

Starting fresh instead? Skip this page — add your first behavior with
`docs/browser-getting-started.md`.

### What works immediately: the parser layer

The parser is 100% Gherkin-compatible (it passes all 50 official Cucumber test
files and rejects all 12 invalid ones), so your `.feature` *files* come over
unchanged. With no config and no step definitions you can already:

- **Check and format** — `sl fmt --check sl/features/` validates every file;
  `sl fmt --write` reformats in place; `sl fmt --canonical` prints the
  canonical form. The roundtrip is lossless, so `--check` is safe to put in CI
  on day one.
- **Stress the grammar** — `sl gherkin fuzz` and `sl gherkin ddmin`
  (`docs/FUZZ.md`) need nothing but the files.

None of that asks you to change a line of your suite.

### What `sl run` tells you

There is no compatibility mode that runs untyped steps. Copy the suite into
`sl/features/` and run it, and the planner binds every step as it always does —
finds that nothing binds — and stops before anything executes:

```
5 binding issue(s) found. Cannot execute.

This reads as an unshifted suite: every selected step is undefined.
ShiftLefter parsed 1 feature file(s), 2 scenario(s), 5 distinct step text(s) — and executes only typed steps.
To shift this suite, run: sl agent-doc adoption
```

Exit code 2 — a planning result, not a failed run. Nothing was launched. Under
`--edn` the same inventory rides the record as a top-level
`:unshifted-suite {:features N :scenarios M :distinct-steps K}`. The distinct
step count is the honest size of the job: it is how many step texts need a
typed definition.

### What shifting means

A step runs when it binds to a **typed** step definition — one that resolves
it to a Subject–Verb–Object triple checked against your project vocabulary at
planning time. Two ways a step gets there:

- **Rewrite it onto a built-in step.** Browser and SMS behavior is covered by
  built-in typed steps; a rewritten scenario needs a subject glossary saying
  who the actors are (`sl agent-doc vocabulary`), and usually intents naming
  what they act on (`sl agent-doc locators`). No Clojure.
- **Write a `defstep` for it**, with `:svo` metadata (`sl agent-doc authoring`
  has the step authoring rules). A matched `defstep` *without* `:svo` still
  binds and runs, and is reported as `:stepdef/untyped` — a warning by
  default, `:error` if you set `:enforcement {:untyped-stepdef :error}`.

What does **not** come over is your step library. ShiftLefter runs built-in
steps or step definitions written in Clojure — not existing
Java/JavaScript/Ruby step code.

### One slice at a time

You do not have to shift the whole suite before anything runs. Once *some*
scenarios plan and others don't, the exit-2 diagnostic says so and names the
flag:

```bash
sl run sl/features/ --hold-unplannable
```

`--hold-unplannable` deselects, at planning, every scenario that an undefined
step, an ambiguous step or a binding error would fail; runs the rest with its
ordinary verdict; and counts the held ones on every surface (`N held` on the
console verdict line, `:held` records under `--edn`, `<skipped message="held:
…">` in JUnit), each held entry naming what held it. It is a per-run CLI flag,
never a config key — a suite cannot quietly configure its way out of being
finished.

Lifecycle lands the same way: global Befores, screenshot capture, and
per-scenario seeding each have a home in hooks (`sl agent-doc hooks`, its
porting note), one slice at a time.

### Where this stands

The table stakes a commercial suite leans on are in place — JUnit XML and HTML
reporting, tag filtering, scenario Before/After hooks. First-class declarative
test fixtures are not (see `docs/README.md` § What 0.5 is (and isn't)).
If you are weighing a production migration, `docs/FIT.md` is the honest read
on whether to move now or watch.

## ShiftLefter Agent Overview

This is packaged agent doctrine for ShiftLefter: concise operating guidance an
agent can read straight from the release artifact, offline, without the project's
private docs. Each topic is a focused subread; `sl agent-doc --list` names them.

ShiftLefter turns Gherkin requirements into executable checks. The stable loop is:
author accepted vocabulary, write feature steps against that vocabulary, validate,
then run. Do not silently invent accepted project truth.

Core commands:

- `sl agent-doc --list` lists packaged doctrine topics.
- `sl agent-doc <topic>` prints one topic.
- `sl orient` orients you in a project: resolved context, diagnostics on the
  project's own truth (config, glossaries, step files, stepdefs against the
  glossary, macros, setup declarations), validate/run commands, and pointers
  to these topics. It does not read your features — `sl run --dry-run` is the
  gate for them.
- `sl doctor` probes the MACHINE (orient's machine-side counterpart):
  chromedriver↔Chrome version lockstep, `~/.shiftlefter/config.edn` validity,
  extra-dependency adapters present when configured, daemon health, orphaned
  chromedriver processes, `sl/lib` jar sanity. `sl doctor --list` prints
  exactly what is and isn't checked; `--edn` is machine-readable. Exit 0 =
  healthy, 1 = issues found. When runs fail for machine-shaped reasons
  (browser won't start, versions drifted), run doctor before debugging.
- `sl glossary` lists the RESOLVED vocabulary (subjects, verbs, objects) with
  per-entry provenance; `sl explain <name>` resolves one name — kind, def
  site, frames, per-interface bindings including missing ones. See the
  `resolution` topic.
- `sl run <path>` executes features.
- `sl run <path> --dry-run` binds every step without executing — the cheap
  validation pass to run before a real browser run. Add `-v` for the step
  plan on stderr (`plan:` — per scenario, each step → the resolved
  `:subject :verb [:frame] object via :interface` and the stepdef's
  `(file:line)`; expanded macro steps indent under their call); `-vv` adds
  each stepdef's pattern source on a `pattern:` sub-line, the detail for
  debugging a stepdef collision; under `--edn` the summary
  always carries `:plan`, the same listing as data, with `:step/resolved`
  on every bound step (`:interface-type` joins it to `sl explain`'s
  vocabulary) and `:step/macro` provenance on wrappers and expanded steps.
- `sl run <path> --tags TAGS` / `--skip-tags TAGS` runs a tagged subset
  (comma-separated, repeatable; `@` optional; include is OR, exclude wins;
  feature/Rule/Examples-block tags inherit per Gherkin). Filtering happens at
  planning time: deselected scenarios are never bound, and counts/JUnit/EDN
  reflect only the selection. `--dry-run` plus a filter previews the selection
  (console appends `; M filtered out by tags`; EDN gains a `:filtered-out` key).
- `sl run <path> --junit-xml PATH` also writes a CI-ingestible JUnit XML report
  (config mirror `[:runner :report :junit-xml]`; the flag wins). It rides
  alongside console/EDN. In a single-group run the XML holds a
  `<failure>`/`<error>` iff the run's exit code is nonzero, and a planning
  error (exit 2) writes no file; in a multi-group run (setup.clj, N>1) the
  file covers only the groups that ran and can be all green beside exit 2 —
  so gate CI on the process exit code, not the report's presence or
  greenness (see ERRATA E009).
- `sl run <path> --html PATH` also writes a self-contained HTML run report
  (config mirror `[:runner :report :html]`; the flag wins). One file, no
  external requests — open it via double-click/`file://`, attach it to CI
  artifacts. Its embedded EDN data island (script type `application/edn`) is
  machine-readable: the full run-ctx + per-scenario envelopes, greppable and
  `edn/read-string`-able straight out of the file. Renders with JavaScript;
  without JS the island is still readable via view-source. Very large runs
  (thousands of scenarios) build a big DOM and will scroll sluggishly.
- `sl run <path> --capture kind=policy,…` captures artifacts into the run's
  results directory (config mirror `[:runner :capture]`; the flag wins as a
  whole value). Kinds are adapter-contributed — the WebDriver backend
  (`:etaoin`, the default) provides `screenshot`, `console`, `page-source`;
  the Playwright backend provides `screenshot` and `page-source` but not
  `console` (no browser-side buffer to drain there — Playwright console is
  listener events; the subscription-shape design is sl-lam0). A configured
  kind supported by none of a group's adapters gets a per-group plan-time
  warning (`:capture/adapter-unsupported`, visible in dry-run previews);
  policies are `never` (default),
  `on-failure` (fires at the failing step's instant, capturing ALL live
  browsers), `every-step` (the film strip: one capture per step, following
  the acting subject; no-SVO steps capture all live). Console is a
  destructive drain: per-step under `every-step` (each file holds exactly
  that step's entries, plus a final tail sweep), once post-steps when red
  under `on-failure`; Chrome/Edge only, other drivers no-op. Refs render as
  attachments in the human report surfaces (HTML, JUnit, console) and the
  `--edn` summary carries them all in its top-level `:attachments` index
  (docs/REPORTS.md § The machine-record contract). A capture-infrastructure failure on an
  otherwise-green scenario flips it to `:error`, capture-attributed —
  check `:data {:kind … :capability …}` to triage "all N errors are
  capture-attributed; ship, fix harness". Capture time never pollutes step
  durations. Dry runs and config-less runs never capture.
- `sl run <path> --max-parallel N` runs up to N scenarios concurrently (config
  mirror `[:runner :max-parallel]`; the flag wins; default 1 = sequential).
  Results and console output are identical to a sequential run — only
  wall-clock changes. Scenarios tagged `@serial` are exclusive: they run one
  at a time after the parallel batch (a feature-level `@serial` marks each
  scenario individually, NOT the feature as an atomic block). Scenarios that
  wear costumes or touch a shared-impl interface are auto-serialized the same
  way (a notice line says so).
- `sl fmt --check <path>` checks that features parse and match canonical formatting.
- `sl verify` is a framework-development tool: in a consumer project it prints a
  notice to stderr and exits 2 (the un-runnable-invocation code — never a silent
  green in CI). Use `sl orient` to check the project and `sl run --dry-run`
  to check the features against it.

`sl orient --edn` dumps the entire project projection as one EDN value — the
machine-readable feed for a planning or disposable sub-agent reasoning over the
project's whole shape (coverage, negative space) rather than editing it.

Costume custody (projects using `:wears`): the wardrobe
(`.shiftlefter/wardrobe/`) holds live credentials — a costume is as sensitive
as the user's own browser profile. It is gitignored; never commit, copy, or
surface its contents, and it should be excluded from sync/backup tools. While
a costume is worn, its session is drivable by any local same-user process
(attachment is Chrome's debug port — structural). Recommend `sl costume
destroy` for costumes no longer in use.

## Project Layout

The project-contents contract, both directions: what a project brings to
ShiftLefter, and what ShiftLefter writes back. Everything lives behind one
door:

```text
<project>/
  AGENTS.md              agent on-ramp stanza (only via `sl init --write-agents`, marker-guarded)
  .shiftlefter/          framework operational state — self-ignoring under sl init
  sl/                    the ShiftLefter project (yours, committed)
    sl, shiftlefter-*.jar  launcher + jar (installer convention)
    shiftlefter.edn      the ONLY discovered config location
    setup.clj            run/group lifecycle + feature-plan owner (optional, fixed name)
    hooks.clj            scenario-lifecycle registry (optional, fixed name)
    features/            feature corpus default
    glossary/            subjects.edn, verbs/, intents/ (probed defaults)
    steps/               dev-step default
    lib/                 user jars — drop in, they're on the classpath
    results/             written by runs (self-ignoring)
```

### What you bring

Defaults are relative to the config root (`sl/`). Explicit config always wins.

| Artifact | Required? | Default | Override |
|---|---|---|---|
| `shiftlefter.edn` | effectively yes | `sl/shiftlefter.edn`, the only discovered location (git-bounded walk-up) | `-c FILE` |
| feature files | yes | no `setup.clj`: `[:runner :features]` default `["features/"]`; with `setup.clj`: the declared plan IS the corpus | config key / CLI paths (subset of the plan under setup) |
| `glossary/subjects.edn` | in practice yes (none = every actor an unknown subject) | probed at `glossary/subjects.edn` | `:glossaries` — explicit value, *including nil*, used as written |
| intents | in practice, for web | probed at `glossary/intents/` | `:glossaries {:intents …}` |
| verb glossaries | no (built-ins cover) | probed at `glossary/verbs/*.edn`; each file's `:type` is its mount key | `:glossaries {:verbs [paths]}` |
| dev steps | no | `[:runner :step-paths]` default `["steps/"]` | config / `--step-paths` |
| `setup.clj`, `hooks.clj` | no | sibling of the active config, fixed names | none — fixed by design |
| macro registries | with `:macros {:enabled? true}` | `:registry-paths` required; INI files or directories (dir loads every `.ini`, recursive, sorted) | configured paths (0.6 moves INI → typed EDN, hard cut) |
| `lib/*.jar` | no | `sl/lib/` | none — wrapper-owned convention |
| machine config | no | `~/.shiftlefter/config.edn` (chromedriver/chrome paths) | contents yes, location no |

Bare `sl run`: without `setup.clj` it runs the corpus default; with
`setup.clj` it runs the full declared plan. Plan shape is linted before
anything runs — a group matching no files or two groups sharing a label
fails the plan; the same feature in two groups warns.

### User code — the wall

User Clojure enters at three named attachment points, each optional, each
with a fixed discovery rule, each validated at load: **steps**
(config-pointed), **hooks.clj** (sibling-of-config), **setup.clj**
(sibling-of-config, owns the feature plan). A fourth point is reserved for
custom adapters. All user code is trusted, in-process, one classpath;
`sl/lib/*.jar` extends it with no build tooling. `shiftlefter.edn` is
**data only** — code never arrives through config. There is no orchestration
DSL and never will be: `:start` is arbitrary user Clojure, a throw means the
group is skipped honestly and other groups run, and cleanup of half-started
state is yours. Keep `setup.clj`'s top level pure (it is load-file'd even on
`--dry-run`; side effects belong inside `:start`). Dry-run starts nothing —
and binds honestly: a group declares its custom adapters as pure data
(`:adapters [{:name .. :provides [..]}]`, the delta vs the default registry);
the preview binds against the declarations and the registry `:start` returns
is verified to match them (mismatch = planning error
`:setup/registry-mismatch`). An undeclared `:start`-returned registry still
works this release with a preview-blind warning (deprecated shape). The warm
daemon re-load-files `setup.clj`
per dispatch — the framework re-derives everything and sees your file fresh;
state your code establishes outside the file (spawned threads, system
properties, open connections) is yours to manage.

Custom reporting today = consume the machine record (`--edn` stdout stream,
or the full record in `report.html`) — contract and runnable recipe in
`docs/REPORTS.md`; live in-run reaction = hooks; bus observers have no user
path. The data contracts (EDN summary shape, bus
event envelope) are locked — code written against the data survives any
future attachment mechanism.

### What the framework writes

The framework writes only into places it owns (below); files the user owns
are never written unprompted — changes arrive as proposals (SIEVE proposes,
never applies): proposed, never written without an explicit yes. Two
named, marker-guarded exceptions, both the direct object of an explicit
user command (the sl-7dq5 ownership boundary): `sl init --write-agents`
writes the agent on-ramp stanza into `AGENTS.md` (create-or-append between
markers; an existing stanza is never edited; plain `sl init` never touches
it — it prints the offer instead), and `sl costume init` appends the
protective wardrobe line to `.gitignore`.

- `sl/results/<STAMP>/` per invocation: `report.html`, per-scenario
  `attachments/<slug>/`, per-group subdirs under `setup.clj`. Self-ignoring
  (`results/.gitignore` = `*`).
- `--junit-xml`/`--html` flags resolve against the shell cwd; their config
  mirrors resolve against the config root; the flag wins.
- `.shiftlefter/` at the project root: `wardrobe/<name>/` (costumes — fixed
  location, no config key), `daemon.edn`, `daemon.log`, `lib-sig`,
  `spawn.lock`, `dirty-teardown.edn` (failed `:stop` marker, announced next
  run), `sieve/`. Self-ignoring: `sl init` writes `.shiftlefter/.gitignore`
  (`*`) at scaffold time, so a scaffolded project never commits it. A
  project that never ran `sl init` adds `.shiftlefter/` to its own
  `.gitignore` — the framework otherwise self-ignores only `results/`,
  (on `sl costume init`) `wardrobe/`, and the installed binaries: the
  installer writes an `sl/.gitignore` (if absent) covering the jar, the
  `.jsa` CDS archive, and `lib/`, so authored files in `sl/` stay
  committable.

## ShiftLefter Authoring

Subjects are actors. A subject instance is one actor session, such as
`:user/alice`, not just a label. Keep that distinction when writing scenarios:
the subject tells ShiftLefter who is acting and which session owns capability
state. Different instances (`:user/alice`, `:user/bob`) get separate browser
sessions automatically — the instance name is the session key, no setup code.
A persona instance can carry a docstring and its own costume in the subjects
glossary (`{:id :alice :desc "…" :wears :alice-chrome}`); run
`sl explain user/alice` to see which persona to use in which circumstances.

A step may be annotated with an interface instance, for example
`[:web]` or `[:admin-console]`. The annotation names an entry in the config's
`:interfaces` map — an execution target; the entry's `:type` selects which
verb vocabulary applies. Interface TYPES own verb vocabularies; every
configured instance of a type shares that vocabulary. Do not assume a verb
valid for one type is valid for another. Unannotated steps default to the
type-named instance when a type has several instances.

Step definitions bind text to code. Prefer steps that describe user intent and
project vocabulary over implementation detail. Custom steps should match the
accepted subject, verb, and object language already present in the project.

The step text itself follows one marker grammar — quotes mean literal,
unquoted Capitalized names mean glossary, `{name}` means a carried value,
`/…/` means a pattern. The full rule set, slot by slot, with every reserved
form: `sl agent-doc grammar`.

If a needed subject, verb, object, or intent is missing, report the gap and use
the bootstrap/reconciliation workflow. Do not make the vocabulary look accepted
just because a plausible phrase exists.

### Writing a step definition

`defstep` binds a regex to a function. The first argument is always `ctx` (the
scenario context map); the remaining arguments are the regex capture groups, and
**captures are always strings**. The function must **return `ctx`** (or an updated
copy) — forgetting to return it breaks the chain. Throw to fail the step.

```clojure
(ns steps.cucumbers
  (:require [shiftlefter.stepengine.registry :refer [defstep]]))

(defstep #"I have (\d+) cucumbers"
  [ctx n]
  (assoc ctx :cucumbers (parse-long n)))   ; captures are strings — parse them

(defstep #"I should have (\d+) cucumbers"
  [ctx n]
  (assert (= (parse-long n) (:cucumbers ctx)))
  ctx)                                       ; return ctx
```

Attach `:svo` metadata so the step resolves to a typed triple — a matched
`defstep` without it still binds and runs, reported as `:stepdef/untyped`
(`:warn` by default).
`:$1`, `:$2` reference capture groups by position. `:interface` names the
interface TYPE the verb belongs to — never a config instance name or an
adapter:

```clojure
(defstep #"^(\S+) clicks (.+)$"
  {:interface :web
   :svo {:subject :$1 :verb :click :object :$2}}
  [ctx subject object]
  ...)
```

#### Timing: the three-clause doctrine

Oracles retry patiently; mutations never retry; negation never waits. A custom
step that OBSERVES something asynchronous never hand-rolls a sleep/poll loop —
it calls the kernel in `shiftlefter.step`:

```clojure
(require '[shiftlefter.step :as step])

;; observe-and-judge: the predicate RETURNS the observation, :until judges it
(defstep #"the export job (\S+) has finished"
  [ctx job-id]
  (step/poll-until ctx #(fetch-job job-id)            ; => {:state "running" :pct 85}
                   {:until #(= "done" (:state %))})
  ctx)
```

`poll-until` polls at the resolved interval/deadline (`:timing` config,
instance > interface > global > default — 30s/500ms bare) until `:until`
accepts the predicate's return. **Return the observation; let `:until`
judge it.** On timeout it throws a structured `:step/poll-timeout` through
normal step reporting — elapsed, deadline, deadline SOURCE, and the last
attempt through exactly one of two channels: `:last-value`, the last thing
the predicate returned (here `{:state "running" :pct 85}` — the diagnosis,
not just "timed out"), or `:last-error`, the last exception a
`:retry-error?` predicate accepted as a not-yet (the built-in browser
oracles ride this channel; your own steps rarely need it). `poll-until`
returns the observation that satisfied `:until`, so the step can use it.
Never wrap a mutation in it; never poll a bare negation (waiting-for-gone =
poll a negated predicate, explicitly). `(step/timing ctx)` reads the budget
without polling.

Footnote — the nil-to-continue form (`(step/poll-until ctx #(when done? …))`,
no `:until`) still works, since the default test is truthiness, but it
**leaves `:last-value` empty on timeout**: a predicate that returns nil to
keep polling has thrown away what it saw. The timeout record says so
(`:hint "pred returned nil to continue; return the observation and pass
:until to populate :last-value"`). Prefer the form above.

#### Evidence in a custom adapter: log the attempt, then the outcome

If your adapter feeds an evidence log — a transcript a capture kind dumps
when a scenario fails — record the attempted operation **before** executing
it, then record the outcome. A helper that logs only after a response
arrives has a structural blind spot: the fatal request (connection refused,
timeout, DNS failure) is exactly the one that never gets a response, so the
trail ends one line before the moment of death. The first real `:api`
adapter we built hit this: the service was killed mid-run, the capture fired
faithfully, and the transcript's last entry was the final *healthy* request.

```clojure
;; BLIND: the fatal request never reaches the log
(defn request! [impl req]
  (let [resp (http/request req)]
    (log-entry! impl req resp)          ; never runs when http/request throws
    resp))

;; HONEST: attempt first, outcome second — a refused request appears
;; in the capture with its failure noted
(defn request! [impl req]
  (let [entry (log-attempt! impl req)]
    (try
      (let [resp (http/request req)]
        (log-outcome! impl entry resp)
        resp)
      (catch java.io.IOException e
        (log-outcome! impl entry {:failed (ex-message e)})
        (throw e)))))
```

The capture fn stays dumb — it dumps whatever the log holds; whether the
moment of death is *in* that log is decided at the helper, by ordering
alone.

### Minimal config

`sl/shiftlefter.edn` — the ONLY discovered location; everything ShiftLefter
(config, features, glossaries, steps) lives in the project's `sl/` directory,
and config-declared paths resolve from it (so `"steps/"` means `sl/steps/`).
Note `:step-paths` lives **under `:runner`** — a top-level `:step-paths` is
ignored. This is one instance of a general lint: any plausible key placed at
the top level (`:step-paths`, `:junit-xml`, `:dialect`, `:unknown-subject`,
…) is ignored by every reader, and the runner warns with the correct nested
path (`did you mean [:runner :step-paths]?`); a key it cannot place gets a
plain unknown-key warning. Warnings, never errors — a newer config must
still run on an older version. Under `--edn` the same lints ride the record
as `:config-lints`, and `sl orient` reports them too. (Warned since 0.5.2;
older versions ignore silently.)

```clojure
{:runner {:step-paths ["steps/"]}

 :interfaces {:web {:type :web :adapter :etaoin}}
 ;; Glossaries: sl/glossary/{subjects.edn,verbs/<type>.edn,intents/} are
 ;; discovered automatically when :glossaries is unset; an explicit map
 ;; overrides the convention wholesale.
 ;; Enforcement levels only — absent = the defaults; presence enables nothing.
 :enforcement {:unknown-subject :warn}}
```

A user `:interfaces` map is the **complete** set — it replaces the builtin
defaults wholesale (no `:interfaces` key = builtin defaults, today the
`:web`/`:etaoin` instance; `:interfaces nil` = explicitly zero). Per entry:
`:default` includes the shipped builtin def of that name verbatim (no
overrides through the sentinel), and a full map is used as-is under any
name — including `:web`, which then fully shadows the builtin. A user map
and a builtin def are **never merged**, and a full map must declare its
`:type` (never inferred from the name — `:admin-web {:type :web …}` is a
second browser instance). `:default` under a name with no builtin is a
planning-time config error, and the `sl/` namespace is reserved for
builtin interface names and types. So a project that declares only `:sms`
has exactly one interface, and `sl orient` says so:

```clojure
:interfaces {:web :default                      ; keep the builtin browser
             :sms {:type :sms :adapter :sms-mock}} ; bring your own
```

### Reserved tags

Tags are free-form except for a closed reserved set. Every tag splits on
its first `=`: the key is left, the value is right (`@env=prod` is key
`env`, value `prod`); `@` opens a tag and never appears inside one. In
`--tags` / `--skip-tags`, a bare key matches every tag of that key
(`--tags @env` selects every `@env=*`); `key=value` matches exactly.

| Tag | What it does |
|---|---|
| `@serial` | The scenario runs alone (never alongside another) under `--max-parallel`. Takes no value. |
| `@hook=NAME` | Runs the named lifecycle hook from `hooks.clj` around the scenario (`sl agent-doc hooks`). |
| `@wip` | A hold: the scenario does **not run**. The author's word while drafting; temporal. A value is optional and kept as a note (`@wip=half-done`). Named in `--tags`, it runs. |
| `@skip=REASON` | A hold: the scenario does **not run**, indefinitely. The reason is required — a bare `@skip` still holds but warns on every run, because reason-free holds rot. Named in `--tags`, it runs. |
| `@blocked=REF` | An expected failure: the scenario **runs**, and a failure or an unobserved run is HELD with what was measured (`blocked by REF — failed at step 2: …`), never counted against the build. If it **passes**, that is XPASS: the claim is stale, the run is exit 1 with `blocked scenario passed: remove @blocked=REF or reopen REF`. A harness error is never excused by the tag (exit 4, tag visible). The REF is required (a bare `@blocked` warns); `{:runner {:ref-url "https://tracker/{ref}"}}` renders it as a link in the record and the HTML report — nothing is fetched. |

Every hold is counted and visible on every surface: the verdict line
(`6 scenario(s): 1 passed, 5 held (1 wip, 2 skip, 2 blocked)`), the
`--edn` record (`:held [{:scenario … :reason :wip|:skip|:blocked :tag …
:note|:ref … :outcome …}]` and `:counts :held`), JUnit (`<skipped
message="held: …">`), the HTML page (a HELD row). An agent cannot hide a
failure by tagging: never add `@skip` without a reason, never add
`@blocked` without a reference, and remove a `@blocked` tag the moment
the run says XPASS. Cucumber's `--wip` differs in one way: theirs fails
the build when a wip scenario passes, ours never runs a wip scenario
unless it is named, because a half-written scenario passing is not a
signal.

Every selected scenario held is an empty selection — exit 2, the count in
the message — because exit 0 is existential.

### Common mistakes

| DON'T | DO |
|-------|-----|
| `(defstep #"..." [n] ...)` | `(defstep #"..." [ctx n] ...)` — `ctx` is always first |
| Forget to return `ctx` | Return `ctx` or `(assoc ctx ...)` from every step |
| `:step-paths` at config top level (warned since 0.5.2, ignored either way) | Nest it under `:runner` |
| `When :login-form submits` | Subjects are actors: `When :user/alice clicks Login.submit` |
| Compare a capture as a number | `(parse-long n)` first — captures are strings |
| Hand-roll `Thread/sleep` or a polling loop in a step | `(step/poll-until ctx observe {:until done?})` — rides the `:timing` ladder, fails legibly with the last observation aboard |
| Poll with a predicate that returns nil to keep going | Return what you observed and pass `:until` — a nil-idiom timeout carries no `:last-value` (the record's `:hint` says so) |
| Retry a click/type/send that "flakes" | Mutations never retry — fix the oracle before it, or the app |

### URL assertions beyond the built-in frames

`should be on <X>` asserts the REGION: normalized path + fragment, query
string ignored (query is state, not region), host ignored, trailing slash
normalized. **Quoted = literal, always; bare = ref**: a bare intent name
(`should be on Feed`) resolves via the intent's `:location`; a quoted value
(`should be on '/feed'`) is a literal. `should be on exactly '<url>'` asserts the exact resource + state
structurally: full URL required, path and fragment exact, query compared as a
multimap — cross-key order insignificant, duplicate-key value order
significant. It takes a quoted literal or a captured `{binding}` token
(`should be on exactly {resetLink}`); bare intent names stay region-only.

Anything more exotic — percent-encoding normalization, host-case rules,
byte-exact string comparison — is deliberately not built in. Write a custom
step assertion (`defstep` + the browser's current URL) for the case at hand,
or petition for a third frame if the need is general.

### Recording why: the provenance convention

A scenario or glossary entry may carry a pointer to the reason it exists —
the ticket, decision, or conversation that motivated it. Two forms:

- a value-shaped tag: `@because=CHK-4412`
- a comment on its own line, directly above the thing it explains:
  `# why: <free text>`

```gherkin
@because=CHK-4412
Scenario: Guest checkout survives an expired session
  # why: carts were lost on session expiry twice in 2025 — CHK-4412
  Given alice opens the browser to Checkout
```

In EDN glossary files, the same convention is an EDN comment above the
entry: `;; why: renamed from "basket" — PROD-88`.

The pointer is opaque. `@because=` is an ordinary tag and `# why:` is an
ordinary comment: nothing parses, validates, or resolves either one, and
planning never checks the pointer against anything. This is a documented
convention, not a schema — it exists so rationale accretes in the corpus
from day one, and it may be promoted to a first-class annotation when
use-case artifacts land. Until then, write the pointer for the next
reader, not for the machine.

Comment placement matters: put `# why:` on the line above the step or
scenario it explains. The canonical formatter attaches every comment to the
construct that *follows* it, so a comment above a step travels with that
step through `sl fmt` — while a comment after a scenario's last step
belongs to the next scenario. One current limit: don't place a comment
between a step and its data-table rows — the parser rejects it there.

## The Authored Grammar

In a ShiftLefter step, punctuation is meaning. Every marker — quotes, braces,
slashes, a capital letter — tells the framework (and the next person reading
the scenario) exactly what a token is, before anything runs. There is one rule,
it holds in every slot, and it exists so that nobody ever has to guess:

- `'…'` (single quotes) — **content, literal, always.** The characters between
  the quotes, exactly as written, no matter what they look like.
- `Capitalized.dotted` (unquoted) — **structure.** A name from your glossary:
  an intent, an element, a location, a key. It must resolve at planning time;
  an unknown name is a plan error with a did-you-mean.
- `{name}` — **content in motion.** A value from the scenario data plane,
  captured earlier (or provided by a hook) and consumed here.
- `/…/` — **a content pattern, inline.** A regex to match against observed
  text; `(?<name>…)` named groups inside it produce `{name}` bindings. The
  same slot takes a `Capitalized.dotted` element reference instead, and then
  the pattern is the element's declared `:shape` — the primary form; inline
  is the escape hatch.
- Bare lowercase words — the step language itself (`fills`, `with`,
  `should see`).
- `:alice` / `:user/alice` — the subject, the actor whose session runs the
  step. `[:web]` at the head of a step — an interface tag naming the config
  instance the step executes on (its `:type` picks the vocabulary).

That's the whole grammar. A quoted token never resolves to anything; an
unquoted capitalized token always must. You can read any step cold and know
which parts are your app's vocabulary and which parts are this scenario's data.

### Two layers: structure and content

Everything stable about the system under test lives in the **structure layer**:
subjects, interfaces, intents and their elements, named locations, verbs, key
names. Structure is glossary-owned and closed-world — every structural token is
checked when the suite loads, and structure changes when your app changes
shape.

Everything that varies scenario-to-scenario lives in the **content layer**:
values you type in, text you expect to see, values captured at runtime and
carried forward. Planning validates content's *plumbing* — every consumed
`{name}` has a producer, every pattern compiles, every literal is unambiguously
literal — but never its *truth*. Whether the page really says "Welcome" is the
run's job.

### Slot by slot

#### Element slots — structure only

`fills Login.code with '123456'` — the element is an unquoted glossary
reference. `Login.cdoe` is a plan error with a suggestion. A quoted
`'Login.code'` is not admitted here: element slots take vocabulary, not
literals, so the step doesn't match — and the undefined-step diagnostic
says why: if the unquoted name resolves in your glossary, "Did you mean
Login.code (unquoted)?", otherwise that the slot takes glossary refs, not
literals.

#### Value slots — content only

`fills Login.code with '123456'` or `fills Login.code with {code}` — a quoted
literal or a binding token, nothing else. Some consequences worth knowing:

- `'{code}'` is the six characters `{code}` — quoted is literal, always.
- `'say "hi"'` is fine; a double-quote inside a single-quoted literal is an
  ordinary character.
- `'Don''t have an account?'` — a literal `'` inside a literal is written
  doubled, SQL-style: `''` inside a nonempty literal is one quote character.
  The doubled pair must be adjacent, which is what keeps steps with several
  quoted slots unambiguous. `''''` is the one-character literal `'`. There
  are no backslash escapes — `''` is the whole escape grammar.
- `"x"` (double quotes) is **reserved** — it is not a quote form in this
  grammar, and the step won't match. The diagnostic teaches the rule and,
  when swapping the quotes would produce a real step, quotes the corrected
  text.
- `'x` (unbalanced quote) won't match either; the diagnostic says the
  literal may be unclosed, with the closed form when that fixes the step.
- `''` (empty literal) is not admitted — "put nothing in the field" wants a
  verb (`clears`), not an empty value. The diagnostic points at the verb,
  naming your element when it can: "to empty a field: clears Login.code".
  (Only the *bare* `''` is refused; inside a nonempty literal, `''` is the
  doubling escape above.)
- `with Welcome` (unquoted ref-shape in a value slot) matches nothing — there
  is deliberately no named-value registry.
- Binding names are born as Java regex group names: a letter, then letters and
  digits. `{order-number}` is impossible (no hyphens); `{orderNumber}` is the
  convention.

#### Location slots — and why `exactly` is different

`opens the browser to Login` (a located intent), `to '/login'` (a literal),
`to {resetLink}` (a captured URL — the magic-link flow). Location slots accept
both layers, and the two location assertions split on purpose.

**Relative literals resolve against `:base-url`.** A schemeless literal —
hand-typed or captured into a `{token}` — resolves per RFC 3986 relative
resolution against the interface's `:config :base-url`: `'/login'` is
root-relative, `'Login'` becomes `…/Login`, and an absolute URL passes
through untouched. (One RFC consequence worth knowing: `'example.com'` is a
relative *path*, so it resolves to `…/example.com` — a host needs its
scheme.) This applies where a full URL is required — navigation and
`exactly` — and there the framework tells you when it can't: a relative
literal with no `:base-url` configured is a structured error naming both
exits (add `:base-url` to the interface config, or use an absolute URL).
Region assertions compare regions, so they never need a host — `should be
on '/secure'` works with or without a `:base-url`.

One guard rail on the boundary between the layers: quoted is literal, always —
so `to 'Login'` is the literal path `Login` (resolved like any relative
path), not the named location and not its declared `:location`. When the name
inside the quotes actually resolves as a named location in your glossary,
validation warns with "Did you mean Login (unquoted)?" (under the same
`:unknown-object` setting as the other location-ref checks).

**A named location is a region, not a URL.** When you declare that `Login`
lives at `/login`, you're naming *every URL that counts as being there* — with
tracking parameters, with a `?next=` redirect target, with a session token in
the query string. `should be on Login` asks one question: is the browser
somewhere in that region? That's almost always what a scenario means.

**`should be on exactly` compares one URL value, character by character** —
scheme, host, path, fragment, and the full query string. That's the right tool
when the URL itself is the observed behavior: the address a magic link opened,
a redirect target you captured a moment ago.

So why does `exactly` refuse a name like `Login`? Because a region doesn't
carry the details a full-URL comparison needs. If `exactly Login` were
admitted, the framework would have to fill in the missing parts — and every
fill-in is a hidden assertion you never wrote: *no query string*, *no
fragment*, *this exact host*. A test that asserts things its author never said
is worse than a test that fails loudly. So `exactly` takes only values — a
quoted URL or a `{captured}` one. A relative value resolves against
`:base-url` first (so `exactly '/login?a=1'` is expressible without
hardcoding a host — the base fills in scheme and host, which *you* declared,
not the framework guessed); with no `:base-url`, a non-full-URL value fails
structurally, naming both exits and pointing at the region assertion you
probably wanted.

#### Text slots — content only

`should see the title 'Welcome'` — free text is content, so the slot takes a
quoted literal or a `{binding}` token. `'Dashboard.home'` in a text slot is
the literal string `Dashboard.home`, even though it looks like a reference —
quoted is literal, always. An unquoted bare word here is reserved (a future
release may add named text); today it matches nothing.

#### Key slots — structure, from a closed set

`presses Enter` — key names are W3C `KeyboardEvent.key` values, the browser
interop standard, validated at planning time with did-you-mean. The full set:

`Enter` `Tab` `Escape` `Backspace` `Delete` `Insert` `Home` `End` `PageUp`
`PageDown` `ArrowUp` `ArrowDown` `ArrowLeft` `ArrowRight` `F1`–`F12` `Shift`
`Control` `Alt` `Meta` `Pause` `Clear` `Help` `Cancel` `Space`

One deliberate deviation, and only one: `Space`. The W3C key *value* for the
spacebar is the literal character `" "`, which has no name — and a quoted
invisible whitespace character would be the least legible token this grammar
could produce. So the spacebar answers to `Space`.

- `presses 'g'` — a quoted single character presses that character key (the
  keyboard-shortcut case, unreachable through `fills`).
- `presses ''''` — the doubling rule applies in every quoted slot, so this
  presses the apostrophe character key.
- `presses 'abc'` — a plan error: pressing is one key; entering text is
  `fills`.
- Chords (`Cmd+A`) and key sequences are not yet part of the grammar.

#### Matcher slots — patterns, and who binds

An element can declare the shape of the text it owns, once, in the intents
glossary:

```edn
{:intent "Reset"
 :elements {:smsCode {:bindings {:sms {}}
                      :shape "verification code is: (\\d{6})"}}}
```

`:shape` is regex source, compiled at planning time. A shape with exactly
**one** group binds its value to the element's own name — so the scenario
reads end to end with no second file open: `receives an SMS … matching
Reset.smsCode` produces `{smsCode}`, and `fills Login.code with {smsCode}`
consumes it. A shape with several groups names each one (`(?<orderNumber>…)`)
and those names are the tokens. The SMS element's `:sms` binding is empty: a
message is a readable with no locator, and the shape is all it has. An element
name that carries a single-group shape must be lowerCamel (`smsCode`, not
`sms-code`), because binding names are; element names otherwise read in kebab
or lowerCamel.

Three steps share the matcher slot, and they divide cleanly by what happens
to named groups:

- `captures Checkout.total` — assert **and bind** by the element's declared
  shape: the step fails unless the element's text matches, and every named
  group becomes a `{binding}`. `captures Checkout.total matching /\$(?<total>[0-9.]+)/`
  is the inline form for a one-off pattern. Both on one step is a plan error
  (two declarations of one shape, both sites named); `captures` on an element
  with no shape and no clause is a plan error pointing at the element's line
  with both exits. A `captures` whose pattern has *no* named groups is a plan
  error — a capture that binds nothing has lost the verb's point — and the
  error points you at the assertion below.
- `should see Order.total matching /\d+\.\d{2}/` — **assert only**: format
  assertions (order-number shapes, prices, dates) without inventing a
  throwaway binding. Unnamed groups are the expected shape here. A *named*
  group written inline in this frame is a plan error pointing back at
  `captures`: named groups produce bindings everywhere, and a frame that
  binds nothing can't quietly ignore one. `should see Confirmation.code
  matching Reset.smsCode` — a declared shape as the assertion — is fine:
  the step shows a structure reference, not a producer marker, and still
  binds nothing.
- `receives an SMS … matching Reset.smsCode` (or `matching /code (\d+)/`) —
  the polling assertions accept either shape; all-unnamed inline just earns
  a notice, since `/(\d+)/` plausibly meant `/(?<code>\d+)/`.

A shape is read through the element's binding on the interface that runs the
step: `captures` on the web wants a `:web` binding, an SMS receive wants
`:sms`. Inside any matcher, an embedded `{binding}` token interpolates as the
*escaped literal text* of its value — never as regex syntax; a shape may not
contain one (the glossary is scenario-independent — `\{word\}` is a literal
brace pair). A malformed pattern, inline or declared, is a structured plan
error.

### When a step doesn't match

An undefined step isn't reported bare. The diagnostic classifies why the text
missed and teaches the rule it broke — at most one hint per step:

- double quotes in a slot → literals use single quotes; double quotes are
  reserved
- an unbalanced single quote → the literal may be unclosed (and when doubling
  an interior quote would produce a real step — `'friends' page'` →
  `'friends'' page'` — the hint offers exactly that)
- an empty literal (`''`) → emptying a field wants the `clears` verb, and
  the hint names your element when it can
- an undoubled apostrophe inside a literal (`'Don't stop'`) → a literal
  quote is written doubled (`''`), with the doubled step quoted when that
  repair matches
- quoted ref-shaped content → quoted is literal, always; with a glossary
  check for "Did you mean X (unquoted)?"
- bare words where a value slot expects a value (`fills X with the SMS
  code`) → value slots take a quoted literal (`'...'`) or a binding
  (`{Name}`); offered only when quoting the tail produces a step that
  actually matches
- an undefined step with no structured tokens at all — no `'...'` literal,
  no `{...}` locator, no `Object.ref` — ending in sentence punctuation →
  it probably wasn't meant as a step. Description prose ends at the first
  step keyword (`Given/When/Then/And/But`, or `*`), so prose that opens
  with one lexes as a real step; move prose above the first step or
  rephrase it. Teaching-only — no repair makes prose match, so there is
  never a did-you-mean

When repairing the text produces a step that actually matches, the hint quotes
the exact corrected step. Apostrophes inside *unquoted* words (`the user's
name` outside any literal) never trigger any of this, and a `"` inside a
single-quoted literal stays an ordinary character.

For tooling, the EDN report carries the same hint machine-readably on each
undefined issue: a `:hint` map of `{:type :grammar/… :suggestion "…"}` plus
`:repaired-text` (present only when a repair produced a real match) and
`:did-you-mean`. The envelope is stable; the set of `:type` values grows as
new hint families land — dispatch on the types you know and fall back to
showing `:suggestion`.

### Reserved, on purpose

Some forms are held back deliberately, so today's no-match is tomorrow's
compatible extension:

| Form | Status |
|------|--------|
| `"double quoted"` anywhere | Reserved — not a quote form; won't match, and the hint says so |
| Unquoted bare word in a text slot | Reserved for future named text — won't match; the hint offers the quoted tail when that would |
| Unquoted name on `should be on exactly` | Reserved — see the region explanation above |
| `+` in a key slot (chords, sequences) | Parked pending a real need |
| `''` empty literal | Not admitted bare — the hint points at `clears`. Inside a nonempty literal, `''` is one literal quote (SQL-style doubling) |

### What `--dry-run` promises

Planning (and `sl run --dry-run`) guarantees: every structural name resolves,
every step is a known frame, every consumed binding has a producer, every
matcher compiles, every literal is unambiguously literal. It does not promise
any assertion passes. **Dry-run truth is structural truth** — the run supplies
the rest.

## ShiftLefter Vocabulary

Accepted vocabulary is project truth. Glossaries define subjects and verbs.
Intent files define named objects, regions, and bindings that steps can address.

Subjects are actors. Subject instances are sessions. Interface TYPES own
verbs and their frames; configured interface instances of one type all share
its vocabulary. Frames type argument shapes, never authorization — who may
do what is discovered by substituting actors and observing the system's real
response, not declared in vocabulary. Intents name objects or regions that an interface type can
target.

The subjects glossary is a plain EDN file. Types with `:instances` group
sessions under a role (`:user/alice`, `:user/bob`); a type without `:instances`
is a singleton, used directly:

```clojure
;; glossary/subjects.edn
{:subjects
 {:user  {:desc "Standard user" :instances [:alice :bob]}
  :admin {:desc "Administrator"}}}
```

An `:instances` entry may also be a persona map — a user with an optional
costume and a docstring: `{:id :alicia :desc "Spanish-first admin reviewer"
:wears :alicia}`. The `:desc` surfaces in `sl explain` and `sl glossary
subjects` (use it to pick the right persona); `:wears` binds that persona to
a costume, resolving instance > type — a type-level `:wears` is an
inheritable default, a persona's own `:wears` wins, `:wears nil` opts out.

Declare each costume's interface INSTANCE in `shiftlefter.edn`:
`:costumes {:finance {:interface :web}}`. Plan-time lints then enforce the
costume doctrine statically: wearing a costume on a different instance than
it is declared for is an error (with a did-you-mean), two targets sharing a
`:wears` in one scenario is an error, and a worn-but-undeclared costume is
a warning that teaches the declaration to add.

Project verbs extend the built-in set in `glossary/verbs/*.edn` files; each
file declares its own `:type` — the required, authoritative mount key, any
keyword including namespaced ones (a same-named project verb replaces the
builtin entry wholesale, frames and all — `sl glossary` marks such entries
`config-override`); intents live under `glossary/intents/` (all under
`sl/`, next to the config — these conventional paths are discovered
automatically when `:glossaries` is unset). Once an intents glossary is
configured (declared or discovered), object checking defaults on at `:warn`
(`:enforcement {:unknown-object …}`): an unresolvable intent reference — an
unknown intent, an unknown element, an element with no binding for the
selected interface — is a planning error (exit 2) with a did-you-mean AND the
def-site (`Declared in: sl/glossary/intents/login.edn:4`); free text on an
intent slot warns and names the fix (`:object-kind :text` on the frame);
`:off` silences. Raw locators ride their own `:raw-locator` kind (same
conditional default) and, at `:warn`/`:error`, name the intent element bound
to the same locator. Every did-you-mean on every path — actor, verb,
interface, intent, capture, config key, and a misspelled verb in step text —
names where the suggested thing is declared. The full file formats and
validation model are in `docs/SVO.md`.

Partial vocabulary is normal. A project may have accepted subjects but missing
verbs, or accepted verbs but incomplete intents. Treat that as useful diagnostic
state, not permission to invent the rest.

When vocabulary is incomplete, say what is known, say what is missing, and route
new claims through SIEVE/bootstrap and proposal reconciliation before treating
them as accepted.

## ShiftLefter Locator Policy

Prefer intent references when accepted truth exists. An intent reference points
to a named project object or region and lets the project own how that object is
located for each interface.

Raw EDN locators are a fallback, not the normal authoring target. They are useful
for experiments, tiny examples, and cases where no accepted intent exists yet.
They are also easier to make brittle.

Do not replace an accepted intent reference with a raw selector just because the
raw selector is visible in a page. That loses project vocabulary and makes future
maintenance harder.

If an object is missing from accepted intents, record the gap and use the
bootstrap/reconciliation workflow. Do not silently promote a guessed locator into
accepted truth.

The same preference applies to URLs: navigation and region assertions
(`opens the browser to`, `should be on`) accept a bare intent name (`Feed`,
unquoted) resolved via the intent's `:location` binding plus the interface's
`:config :base-url` — prefer that over hardcoding URLs in step text. Quoted
values are always literals (quoted = literal, bare = ref — the same rule as
element slots); literal URLs remain the fallback, exactly like raw EDN
locators.

### Choosing a web locator strategy

The above is intent references vs. raw locators. This is which raw locator to use
once you reach for one — authoring an intent's web binding, or a tiny example with
no accepted intent yet.

A locator is a hypothesis about what stays stable. Bind to the most stable thing
you are committed to keeping true about the element. Brittleness is not one axis:
a break on a cosmetic refactor is noise; a break because an element lost its
accessible name is signal. Prefer locators readable as intent — legible locators
are repairable.

Two rankings; which applies depends on whether you can change the markup.

You control the source (can add/enforce markup):

1. Dedicated automation attribute (`data-testid`/`-test`/`-cy`/`-qa`) — canonical,
   paired with role + accessible name as validation.
2. ARIA role + accessible name.
3. Label (form fields).
4. Stable human-authored id (never hashy/generated).
5. Visible text (when the text is the requirement).
6. CSS attribute / light structural (`button[type=submit]`).
7. CSS class / layout — scoping prefix only, never identity.
8. XPath — last resort, relational/axis only.

You cannot modify the app (third-party/legacy — borrow, do not manufacture):

1. ARIA role + accessible name.
2. Label.
3. Visible text, scoped.
4. Stable id (only if human-readable, stable-looking).
5. CSS attribute selectors (`[name]`, `[type]`, `[aria-*]`, `[href]` over classes).
6. CSS class / structure (only if semantic and stable).
7. XPath (tables, sibling relations, ugly DOMs — scope it, mark fragile).

The dedicated attribute is canonical when you own the markup because this durable,
agent-maintained, often multi-locale layer pays most of its cost in maintenance
churn, and an owned contract — a `data-testid`, effectively an API endpoint in the
DOM — insulates against the copy/layout/i18n changes that otherwise force
re-derivation. The price: a test-id can stay attached while the real control
breaks, so always pair it with role + name as validation, and name by product
intent (`domain.object.action`, e.g. `checkout.submitOrder`), never by
implementation (`greenButton`). Enforce uniqueness.

Match exactly the set you mean — often one element, sometimes a known collection
you index into. Aim for a count you can state in advance, not an unpredictable one.

The agent or user may always override the default for a given element. Record why.

Other interfaces (iOS, Android, REST, …) narrow the menu but keep the rule: bind
to an owned, intent-named contract over incidental structure. Carry the
philosophy, not the literal web ranking.

Full justification and the change-behavior evidence table: `docs/LOCATORS.md`.

## ShiftLefter Diagnostics

Diagnostics describe the gap between authored steps and accepted project truth.
Treat them as first-class feedback, not noise.

Unknown subject means the actor or instance is not accepted. Unknown interface
means the step's annotation names an interface instance the config has not
declared. Unknown verb means that interface type does not own the action
phrase. Unknown object means the step refers to a target the accepted intents
or glossary do not know. Ambiguous instance means an unannotated step's type
has several configured instances and no type-named default — annotate the
step with the instance it targets.

Parse errors are collected, not thrown: the Gherkin parser accumulates every
error in a file in one pass — invalid tags, bad keywords, orphan tags,
out-of-order structure — and reports the full error vector alongside the
partial AST it could still build. A repair loop can fix everything reported
in one edit instead of fix-one-rerun-discover-the-next; each error renders
with its own location.

Respond by preserving the distinction:

- If the feature text is wrong, fix the feature text.
- If the accepted vocabulary is incomplete, propose vocabulary changes through
  the documented bootstrap/reconciliation path.
- If the implementation is missing for accepted vocabulary, add or fix the step
  definition.

Do not silence diagnostics by inventing accepted subjects, verbs, interfaces, or
objects in place.

## Resolution Queries: sl glossary and sl explain

The files are the DECLARED state; these two commands expose the RESOLVED
state — what a run will believe, before the run. Both resolve through the
run's own config and glossary loaders (never a parallel path), so their
answers cannot disagree with the run they predict. Both accept
`-c/--config` exactly as `sl run` does, and both take `--edn`.

**EDN is the contract.** `--edn` output is the stable machine surface —
one reader-readable map per invocation. The human format is EXPLICITLY
UNSTABLE; do not parse it.

### sl glossary

```
sl glossary [subjects|verbs|objects|duplicates] [path ...]
            [--tags T] [--skip-tags T] [--edn] [-c FILE]
```

Bare `sl glossary` prints three sections; a narrowing argument selects
one. Every entry carries a **provenance marker**:

- `builtin` — shipped with the framework (default verb glossaries)
- `user-file` — declared in a project glossary file
- `config-override` — a project entry that replaced a builtin of the
  same name
- `interface-contributed` — vocabulary an interface family supplies
  (the closed W3C key-name set for frames with `:object-kind :key`;
  implicit objects such as `:sms-message`)

Sections: **subjects** (types + instances), **verbs** (grouped per
interface type, each frame shown as schema — frames are NOT step text),
**objects** (intents plus the interface-contributed vocabulary above).

The output header states the substrate the listing was computed against:
the resolved config path and source, the git sha with a dirty marker
(or an honest "not a repository"), and the EFFECTIVE `:svo` strictness
levels — including the conditional `:unknown-object` default that flips
to `:warn` when intents are configured, which is not readable from any
file.

### Usage markers and dead vocabulary

Listings also bind the feature corpus (parse + bind, never execute — the
same binder FUNCTION a run uses, over a different corpus: the config's
feature tree, not the union a `setup.clj`'s groups would actually
execute, so usage counts can include scenarios no run selects) and mark
every entry with its usage: subjects
and user vocabulary that nothing references show `[UNUSED]`; used
entries show `[used ×N]`. **Builtin vocabulary is never dead** — it is
globally provided, so builtins carry counts but never a deadness
verdict. Deadness is a **full-corpus** fact at a named tree state: the
header states the corpus (file/scenario counts, the git sha, the config
path), and if any feature file fails to parse or any step fails to bind,
the caveat is printed rather than silently under-counting. No corpus at
all → markers are suppressed entirely (never "everything is unused").

**Scoped selection**: positional paths and `--tags`/`--skip-tags` (the
run's own selection grammar) restrict the corpus. Under a selection the
wording weakens to `[not referenced within this selection]` and the EDN
key changes from `:unused?` to `:referenced-in-selection?` — a scoped
verdict is an impact-analysis fact, NEVER a deletion license. Only the
full-corpus voice may say "unused".

### sl glossary duplicates

The on-demand locator-collision report: locator values owned by two or
more intent addresses within one interface, grouped by confidence —
same-intent collisions (`Login.foo` vs `Login.bar`) are high-confidence
real duplicates; cross-intent collisions are likely page-scoped
coincidence (the same `#submit` on different pages is the norm, which is
why this report is never always-on). Equality is structural over the
locator EDN value; semantic aliasing (two XPaths, one element) is out of
scope. Owners cite their defining intent file.

### sl explain NAME

```
sl explain NAME [path ...] [--tags T] [--skip-tags T] [--edn] [-c FILE]
sl explain '{:css "#submit"}' [--edn]
```

One name in, full resolution out. Accepts `click`, `:click`,
`user/alice`, `Login` — every matching kind is reported (subject type,
subject instance, verb per interface type, intent, key name). Per match:
kind, provenance, definition site, frames (schema), and **per-interface
bindings including missing ones** — a frame with no stepdef on a
configured interface is reported as MISSING, not silently omitted.

Definition sites are file-precise for glossary and intent entries (EDN
carries no line info) and file:line-precise where that truly exists —
stepdef bindings and their `bind with:` examples.

Every match also carries its corpus **USAGE**: subjects get the full
actor view — per-instance hits (feature file:line, scenario, the step
text and its pattern — authoring by example), the type rollup, a
multi-actor flag, and co-occurrence pairs (which other actors share
scenarios); verbs and intents get their reference hits. The same
selection parameters apply, with the same wording discipline.

**Explain a locator**: an argument that starts with `{` is read as a
locator EDN value and reverse-looked-up — which intent addresses own it
(element binding, region root, or collection selector), per interface.
Check before minting a new intent binding: a hit means the element is
already named; a miss says "free to mint". Structural equality only.

On a miss: exit 1 with did-you-mean suggestions (edit distance plus
surface-token lookup — `sl explain clicks` suggests `:click` from the
frame pattern "S clicks O"). EDN mode reports `{:status :miss}` with
`:suggestions` on stdout. A malformed invocation (no NAME) exits 2.

### Merge semantics (verified, sl-0gfc)

Project verb glossaries EXTEND the builtin set. On a name collision the
project entry replaces the builtin entry **wholesale** — description and
all frames; there is no frame-level merge, so restating a builtin verb
to add one frame silently drops its other frames. `sl explain <verb>`
shows exactly what survived and marks the entry `config-override`.
`defstep` contributes step BINDINGS, never vocabulary — a stepdef naming
a verb absent from the glossary is reported (`:unknown-verb`, `:warn` by
default — it warns and runs; unknown frames or args on a KNOWN verb stay
hard errors), never an addition.

### Scope

Both commands always resolve: a project with no glossary of its own lists
the framework defaults, and steps that did not bind are named in a `Caveat:`
line because they contribute no usage facts. Macros
contribute steps, not vocabulary — they do not appear here. The
coverage-matrix renders (vocabulary × interface grids) are a future
surface pending a second interface type in real use; the per-intent
`missing bindings:` markers in the objects listing carry the hole data
today.

## Scenario Lifecycle Hooks

Hooks are the escape hatch for lifecycle code around a scenario — seeding or
resetting external state before it runs, capturing a screenshot or scraping a
console after it. Prefer the stronger mechanisms when they exist (a step, the
`setup.clj` orchestration for run-level lifecycle); reach for hooks when the
work genuinely belongs to the scenario boundary.

### Naming: the feature file states what runs around it

Scenarios NAME their hooks with `@hook=<name>` value-tags. Nothing fires
invisibly: for any scenario, "which hooks fire, in what order" is answerable
from the feature file plus one registry file, and `sl run --dry-run` prints
the resolved per-scenario firing list.

```gherkin
@hook=reset-db
Scenario: Purchase with a fresh account
  Given alice opens the browser to 'https://shop.example.com'
```

Tag inheritance follows Gherkin: a feature-level `@hook=` applies to every
scenario in the file; Rule- and Examples-block-level tags nest the same way.
The same hook named at two levels runs once, at the outermost position.
An `@hook=` naming an unknown hook is a planning error (exit 2) reporting
the tag's file and line. Unrecognized value-tag keys (`@foo=bar`) are
ordinary inert tags.

### Registration: hooks.clj

Registrations live in `hooks.clj` next to your `shiftlefter.edn` (both in
`sl/`; discovered
exactly like `setup.clj`; no file = no hooks). It declares `(ns hooks)` and
defines `hooks` — an ordered vector, or a `(fn [config])` returning one:

```clojure
(ns hooks)

(def hooks
  [{:name "audit"                       ;; required, unique
    :global? true                       ;; applies to every scenario, visibly
    :before (fn [{:keys [ctx scenario]}]
              nil)}
   {:name "reset-db"
    :requires-serial true               ;; auto-serialize carrying scenarios
    :before (fn [{:keys [ctx scenario]}]
              {:seed/user-id 1234})     ;; map return merges into ctx
    :after  (fn [{:keys [ctx scenario result]}]
              (when (= :failed (:status result))
                ;; capabilities are still live here (before cleanup)
                nil))}])
```

- `:name` (required, unique) — what `@hook=<name>` resolves against.
  Duplicate names are a planning error.
- `:before` / `:after` — optional; either or both. A pair registered under
  one name unwinds as one frame.
- `:global?` — runs for every scenario, stamped and previewed like any named
  hook; vector order is the execution order among globals.
- `:requires-serial` — scenarios this hook applies to run exclusively under
  parallel execution; reports show the derived `@serial` annotation with the
  hook named as the reason.
- `:provides` — optional vector of binding names this hook's `:before` seeds
  into the scenario data plane. A binding name is a bare keyword, a letter
  followed by letters/digits (lowerCamel by convention, e.g.
  `[:sessionToken]`). A static declaration: it satisfies dry-run's
  consumed-without-producer check for `{name}` tokens. Contribution keys
  fitting that shape mirror into `:sl/bindings` at execution whether
  declared or not.

### Execution order

Per scenario: **Befores → capability provisioning → steps → Afters →
capability cleanup.**

- Befores run outermost-first: globals (registry order), then `@hook=` tags
  in feature → rule → scenario → examples nesting order.
- Befores run BEFORE provisioning — a broken seed hook fails before paying
  browser-launch cost. Befores therefore see no capabilities.
- Afters run AFTER steps but BEFORE cleanup — a screenshot or console-scrape
  hook can reach the live browser via `:ctx`.
- Afters unwind in strict LIFO order of the Befores that ran. If provisioning
  itself fails, every After still unwinds — WITHOUT capabilities, so an After
  must check for the capability it wants, not assume it.

### Payloads and failure semantics

- `:before` receives `{:ctx ... :scenario ...}` (scenario = name, tags,
  source file/line). A map return merges into ctx — the sanctioned way to
  hand data to steps; the report records the contributed keys. nil = no
  contribution.
- `:after` receives `{:ctx ... :scenario ... :result ...}` where `:result`
  is the in-flight scenario result (status, per-step results with durations
  and — on steps whose oracle polled — a `:poll-counts` digest, error). On-failure conditionality is a plain `when` on
  `(:status result)` — there is no separate on-failure hook kind. The
  return is the ATTACHMENTS CLAIM: nil (no claim) or
  `{:attachments [{:attachment/kind :screenshot :attachment/path "..."} ..]}`
  — refs to files the hook wrote, which then ride the scenario envelope,
  render in the human report surfaces (HTML, JUnit, console) and appear in
  the `--edn` summary's top-level `:attachments` index. The contract is
  full-strict: any other return
  (a map with extra or misspelled keys, a malformed ref, a non-map value)
  is `:hook/invalid-return` → scenario `:error`. A claimed file that does
  not exist keeps the scenario outcome but the ref is marked
  `:attachment/error` and a stderr warning fires — evidence loss is never
  silent.
- Both payloads carry `:artifacts-dir` (an absolute path, pre-created)
  when the run has a results directory — write attachment files there and
  claim them; refs inside the run directory render inline/portable in the
  HTML report. The key is absent (not nil) in runs without a results
  directory (no config file) — check, don't assume.
- Before writing a screenshot/console/page-source After hook: DON'T — set
  the `[:runner :capture]` policy instead (see the CLI overview's
  `--capture` entry). Hooks are for one-off evidence the framework
  doesn't own (DB dumps, API traces); evidence owned by a capability you
  provision can instead become a custom capture KIND — a `:capture` entry
  on your setup.clj adapter registry, policy machinery included (worked
  example: `examples/07-custom-capture-kind/`). With `:capture` console
  active, the framework
  owns the destructive console drain — a hook reading the browser's log
  API gets leftovers; read the captured artifact, or use `:on-failure`
  (whose single post-steps drain fires before any After).
- A `:before` throw makes the scenario `:error` (never `:failed`), skips its
  steps, and unwinds only the frames whose Befores succeeded. A `:after`
  throw makes the scenario `:error` even when all steps passed — broken
  cleanup is a lying suite. One failing After does not stop the unwind.
- A `:before` returning anything other than a map or nil is a hook error
  (`:hook/invalid-return`) with the same shape: scenario `:error`, steps
  skipped. Note the entry gets NO unwind frame even though its body fully
  ran — its own `:after` will not run, so side effects the body made before
  the bad return are not unwound by it.
- Every hook that runs is stamped in the scenario envelope and rendered in
  JUnit system-out and the HTML transcript:
  `{:name .. :phase .. :status .. :duration-ms .. :contributed [..]}`.

### Reaching external systems

A hook that needs a library beyond the bundled classpath (the flagship case:
a JDBC driver for a database-resetting `:before`) gets it by dropping the
library's jar — and its dependencies' jars — into the project's `sl/lib/`
directory. Everything in `sl/lib/*.jar` rides the classpath of every run,
cold and warm alike (the daemon restarts itself when the lib set changes).
No build tooling: bring resolved jars, not coordinates.

Shelling out — `clojure.java.shell/sh` to `psql`, `curl`, an internal CLI —
remains an option when a subprocess is genuinely the right tool; it is no
longer the only route to an external system.

## The Execution Lifecycle

Every run is two phases: PLAN, then EXECUTE. `sl run --dry-run` is phase one
exposed — the same plan every run computes, stopped before anything executes.

### The plan phase

Guarantees (structural truth): every structural name resolves; every step is
a known frame; every consumed `{binding}` has a producer; every matcher
compiles; each scenario's hook firing list is resolved from its `@hook=`
tags (and printed under `--dry-run`); plan-shape lints run (a `setup.clj`
group matching no features = error, duplicate group labels = error, the same
feature in two groups = warning). Tag filtering happens at planning time —
deselected scenarios are never bound. Planning does not promise any
assertion passes.

The plan phase never invokes `:start`, `:stop`, or hooks, and never
captures. `setup.clj` IS `load-file`'d so the plan is knowable — keep its
top level pure; side effects belong inside `:start`. Custom adapters stay
visible to this phase via the group's `:adapters` declaration (pure data,
the delta vs the default registry): the preview binds against the declared
shapes, and the registry `:start` returns is verified to match them
(mismatch = planning error `:setup/registry-mismatch`; an undeclared
returned registry is a deprecated shape that warns).

### The execution weave

```text
group (declared order, one at a time)
  :start                      ← the world starts here, not earlier
                                (its registry verified against :adapters)
  parse + compile             ← against the group's adapter registry
                                (declared data, live factories)
  scenarios (parallel-capable)
    Before hooks              ← no capabilities yet
    capability provisioning   ← browsers launch here
    steps
    After hooks               ← capabilities still live
    capability cleanup
  :stop                       ← in a finally — even when scenarios failed
```

Without `setup.clj` there is one implicit suite, no `:start`/`:stop`, same
scenario weave. Befores run before provisioning (they see no capabilities; a
broken seed hook fails before browser-launch cost). Afters run after steps,
before cleanup (capabilities still live), unwinding in strict LIFO order of
the Befores that ran. Every hook that runs is stamped in the scenario
envelope.

### Failure semantics by stage

- Planning failure (unresolved name, unknown frame, consumed binding without
  a producer, unknown `@hook=`, broken plan shape) → exit 2, nothing executes.
- Empty selection (a tag filter matching 0 of N, feature files with no
  scenarios, CLI paths narrowing every group away) → exit 2, checked before
  any `:start` runs; the record carries counts and what was searched. A dry
  run's exit 0 requires a nonempty selection too.
- `:start` throws or returns a malformed shape → group-local planning
  failure; the group is skipped, other groups still run. Half-started state
  is user-owned — the framework can't know what half-started.
- Before hook throws or returns a non-map → scenario `:error` (never
  `:failed`), steps skipped, only succeeded frames unwind.
- Capability provisioning fails → scenario `:error` — same family as a hook
  throw (broken harness ≠ broken app); Afters still unwind, WITHOUT
  capabilities.
- Step fails → scenario `:failed`; `:on-failure` capture fires at that
  instant, before Afters.
- Step throws with `:error/class :observation` (the witness went dark — no
  answer existed: refused, transport timeout, DNS) → scenario `:error`,
  counted `unobserved` (disjoint from the harness's `error` bucket), exit
  4; the step stays `:failed` with the class on its error. The other two
  classes (`:sut` = the app answered WITH an error, `:assertion` = the app
  answered and missed) are recorded and rendered only — scenario `:failed`,
  exit 1. Absent key = unchanged behavior. Builtin SMS/browser adapters
  ship classified; tag your own adapter's throw at its catch site — the
  class is read when that throw reaches the STEP; hook, provisioning and
  capture throws are the harness bucket (`error`), never `unobserved`.
- `{:runner {:halt-on-observation-failure true}}` (default off) → after an
  observation-class scenario, no further scenario STARTS; in-flight ones
  (`--max-parallel`) finish and keep their verdicts, everything unstarted
  (incl. the `@serial` tail) is `skipped`; the summary says `halted after
  scenario N (<name>): observation failure` and the EDN summary carries
  `:halted {:after-scenario N :scenario "<name>"}`. Exit 4 either way.
  The key is `false` | `:group` | `:run` (`true` = `:run`): with `setup.clj`
  groups, `:run` skips every group not yet started (its `:start` never
  runs; the invocation aggregate carries the `:halted` record and the
  skipped groups' rows say `:run/status :skipped`), `:group` halts only the
  group that went dark.
- Ctrl-C (or `sl daemon abort`) → the run **aborts, exit 4**: nothing new
  starts, a running scenario stops at its next step boundary, Afters +
  cleanup + `:stop` still run, every report is written; unrun scenarios are
  `held` (`:held {:reason :aborted}`, counted under `:held`) and the summary
  carries `:halted {:reason :aborted :after-scenario N}`. A second Ctrl-C:
  cold = the crash row (exit 3); warm = the client detaches (130) and the
  daemon finishes the unwind.
- After hook throws or its attachments claim is malformed → scenario
  `:error` even when every step passed. One failing After doesn't stop the
  unwind.
- Capture infrastructure fails on an otherwise-green scenario → scenario
  `:error`, capture-attributed; an already-red scenario keeps its status and
  the ref records the miss.
- `:stop` throws → reported (console + envelope), exit code unchanged: the
  exit code is this run's verdict, already earned by the time teardown runs;
  environment damage is the NEXT run's planning input — which is what the
  dirty-teardown marker is (written now, announced at the next run's start,
  then cleared).
- Any scenario `:error` → exit 4 (run degraded: the harness broke or the
  observation channel went dark — the run proves nothing about the app for
  that scenario), distinct from exit 1 (a scenario failed). Exit 4 is not
  an acquittal: red, blocking; only the indictment of the app is withheld.
- Exit codes aggregate worst-wins across groups: 2 > 4 > 1 > 0. 0/1 are
  verdicts about the app; 2/3/4 are three ways the run failed to be a
  measurement (your request / SL's code / the observation channel).

### Parallelism

Groups are sequential (declared order). `--max-parallel N` is
scenario-grain within one process (default 1; results identical to a
sequential run — only wall-clock changes). Exclusive scenarios run one at a
time after the parallel batch: `@serial`-tagged, scenarios carrying a
`:requires-serial` hook (reports show the derived `@serial` with the hook
named), and costume-wearing or shared-impl-interface scenarios (notice line
says so). There is no built-in CI-level suite sharding.

### Capture timing

`:on-failure` captures at the failing step's instant — before Afters —
across every live capability. `:every-step` captures once per step,
following the acting subject. Console capture is a destructive drain: per
step under `:every-step` (each file holds exactly the entries since the
last drain, plus a final tail sweep), once post-steps under `:on-failure`,
before any After runs. Capture cost is recorded on the ref
(`:attachment/duration-ms`) and never pollutes step durations. Dry runs
never capture.

### The run seed

Every invocation gets ONE seed (positive 64-bit long, decimal): `--seed N`
beats config `:runner {:seed N}` beats generated. Recorded always —
`:run/seed` in every group's `--edn` summary, `:seed` in run-ctx, the HTML
header, one stderr line (`run seed: N`). One deliberate exception: the
daemon's busy-reject summary (exit 2, nothing ran) carries no `:run/seed`
— nothing was seeded. The framework draws no randomness
from it; it is handed to user code: hook payloads carry `:seed`, step
`ctx` carries `:seed`, and `:start` receives a `:seed` key on its config
argument. Need several independent streams? Derive:
`(bit-xor seed (hash scenario-id))` — the documented convention, not
framework code.

### Consuming the run record

The run record = the `--edn` stdout form stream (redirect it — no summary
file is written) plus the run-directory bytes. The summary's top-level
`:attachments` index is the authoritative evidence walk (green-run evidence
appears only there); `:failures` entries carry their own refs inline for
join-free triage — same refs, deliberate duplication. `:run/seed` on every
summary is the run's seed — rerun with `--seed <that value>` to reproduce
user-code randomness. In a multi-group run each group's summary carries
`:group/label` + `:group/index` (join by index, not stream order — the
index is the group's DECLARED position, so under CLI narrowing the numbers
keep their declared values and may have gaps), and one
final `:invocation/exit-code` form carries the suite verdict — read it if
present, else the lone summary's `:run/exit-code`. Building a custom
rendering from the record: `docs/REPORTS.md` (contract + runnable recipe).

Related topics: `hooks` (registration, payloads, attachments claim),
`layout` (which files attach user code, what the framework writes).

## Exit Codes

The `sl run` exit code is a claim about what the run proved. This is the
decision procedure; the reasoning lives in `docs/architecture/exit-codes.md`.

### The table

| Code | Status | Meaning |
|---|---|---|
| 0 | `:passed` | Existential pass: ≥1 scenario selected, every selected scenario ran to a tolerated outcome, none failed or errored (pending tolerated only under `:allow-pending?` — the counts still confess). |
| 1 | `:failed` | ≥1 scenario `:failed` — the app answered and the answer missed the expectation (including `:sut`-classed errors: the app answered *with* an error). Or pending under strict mode. Or a stale `@blocked` claim (XPASS: a `@blocked=REF` scenario passed — the test's claim about the app is what is wrong; still a failing corpus). |
| 2 | `:planning-failed` | Invalid before execution: config/parse/discovery/binding errors, an un-runnable invocation, an empty selection. Pre-execution exclusive — nothing ran. |
| 3 | `:crashed` | Runner crash — an uncaught throwable in ShiftLefter's own code, including one that escapes a scenario's execution machinery (never a scenario verdict; the same exit at every `--max-parallel`, and the crash names the scenario). Anywhere; wins over everything. |
| 4 | `:degraded` | ≥1 scenario `:error` — either the harness's own machinery broke (hook throw, capability provisioning, capture; counted `error`) or a step's adapter classified its failure `:observation` — no answer existed (counted `unobserved`). The verdict about the app is unavailable for those scenarios. |

Precedence: 3 anywhere; 2 pre-execution exclusive per `setup.clj` group;
during execution worst wins, 4 > 1 > 0; across groups the suite
aggregates worst-wins: 2 > 4 > 1 > 0. A suite-level 2 means at least one
group's request was never runnable — earlier groups' evidence is real and
in the report; gate on the exit code, not the report. Under `--edn` a
multi-group run also says this in the stream: each group's summary carries
`:group/label` + `:group/index`, and one final aggregate form carries
`:invocation/exit-code` — the suite verdict, readable without the process
exit (absent in single-group streams, where the lone summary's
`:run/exit-code` is the verdict; absent on a crash).

### What to do on each exit

- **0** — the app met every expectation checked. Done.
- **1** — the app answered and at least one answer was wrong. Debug from
  the report's failure evidence.
- **2** — nothing ran for that group. Fix the invocation, the config, or
  the spec's symbols. Absence of exit 2 is not evidence the spec is
  valid — a fresh element-not-found at runtime (exit 1) may be glossary
  rot or app regression; triage, don't assume.
- **3** — ShiftLefter itself crashed. Trust nothing in the run; file a
  framework bug.
- **4** — ≥1 scenario got no answer. Do not touch product code; check the
  environment, then rerun. Exit 4 withholds the indictment of the product
  because the evidence never reached it.

### Classifying a failure (the razor)

Did the witness channel — the channel the SUT is observed through —
answer?

- Answered, wrong → `:error/class :assertion` → scenario `:failed`, exit 1.
- Answered *with* an error (500, stack-trace page, job state `failed`) →
  `:sut` → `:failed`, exit 1.
- Never answered (refused, transport timeout, DNS) → `:observation` →
  `:error`, counted `unobserved`, exit 4. Classifying silence as
  `:observation` is a refusal to convert silence into evidence.

Give-backs: a late answer that arrives is `:assertion`; a poll that timed
out after successful answers is `:assertion` — `:last-value` present
means the witness was answering, `:last-error` only means it never
answered. An expected event that never occurs through a healthy witness
is `:assertion`; an expected response that never comes is `:observation`.
The one misclassification that lies: marking a delivered answer
`:observation`. Unclassified errors keep default behavior; declining to
classify is always safe.

### Exit-4 triage

The build is red, nonzero, blocking either way. The report names which
scenarios went unobserved — read it before rerunning. The same scenario
unobserved run after run while its siblings pass: suspect the SUT's
responsiveness, not the network.

`{:runner {:halt-on-observation-failure true}}` (run-level config,
default off): after a scenario finalizes observation-class, no further
scenario starts; in-flight scenarios finish and keep their verdicts, the
rest are `skipped`; the exit code is 4 either way. The key is a tri-state
`false` | `:group` | `:run` (`true` reads as `:run`): with `setup.clj`
groups, `:run` skips every group not yet started — its `:start` never
runs, its aggregate row says `:run/status :skipped` — while `:group`
halts only the group that went dark and lets the siblings run.

A classified driver failure's record (`Data:` on the console, `:error :data`
under `--edn`) carries the driver's answer only: what was asked (`:type
:status :method :path :host :port`) and what it answered (`:response {:value
{:error … :message …}}`), plus the classification keys — never the driver's
process map or its native stacktrace. If you ever need the full driver data,
file an issue saying what you needed it for. Meanwhile it is one `ex-cause`
away at the REPL — the step runner catches a step's throw into a result map,
so go through the browser protocol directly (on the test classpath,
`java -cp "$(clojure -Spath -A:test)" clojure.main`):

```clojure
(require '[shiftlefter.adapters.etaoin :as eta]
         '[shiftlefter.browser.protocol :as bp]
         '[shiftlefter.browser.errors :as errors])
(def cap (:ok (eta/create-browser {:headless true :page-load-timeout-ms 3000})))
;; the raw driver exception, unclassified:
(try (bp/open-to! (:browser cap) "http://127.0.0.1:59999/")
     (catch clojure.lang.ExceptionInfo e (ex-data e)))
;; or the classified record with the full data as its cause:
(try (errors/classify-navigation #(bp/open-to! (:browser cap) "http://127.0.0.1:59999/")
                                 "http://127.0.0.1:59999/")
     (catch clojure.lang.ExceptionInfo e (ex-data (ex-cause e))))
(eta/close-browser cap)
```

Related topics: `lifecycle` (failure semantics by stage, the execution
weave), `builtins` (the pre-classified built-in step families).

## ShiftLefter SIEVE Bootstrap

SIEVE is the workflow for turning observed or proposed interface facts into
reviewable project vocabulary. It is not a license to silently accept guesses.

**Status in 0.5: preview.** SIEVE's interactive tooling is a development/REPL
surface; there is no `sl` subcommand for it yet. What you can do today: name the
missing vocabulary, draft the glossary/intent edits as an ordinary reviewable
change (a patch or PR against the project's `sl/glossary/` files), and let a human
accept it. The discipline below describes the workflow's shape either way.

When accepted vocabulary is missing, collect evidence, draft candidate subjects,
verbs, intents, objects, and bindings, then reconcile the proposal. Applying a
proposal writes selected accepted changes into the project. A later projection or
agent prompt can then report those changes as accepted truth.

Before apply, drafts remain drafts. Agents should name the gap, explain the
candidate evidence, and leave unresolved or conflicting claims unresolved.

Use this path when authoring needs vocabulary that is not already present. Do not
hide missing vocabulary by writing raw locators or custom phrases that bypass the
project language.

## ShiftLefter Built-in Vocabulary

Generated reference for the framework's built-in verbs, frames, step
patterns, and adapters. A consumer project has only the jar, so this
vocabulary cannot be discovered by grepping the project — it is supplied
here as static, packaged reference.

This file is GENERATED from the framework's default glossaries
(`verbs-web.edn`, `verbs-sms.edn`), the step registry, and the adapter
registry. Do not edit it by hand — edit the source and regenerate with
`clojure -T:build gen-builtins`.

Sections are grouped by interface TYPE for targeted subreads. Within
each type: the adapters that back it, the verbs and their frames (each
frame is one accepted argument shape), then the step grammar (regex
source) and the verb/frame each pattern maps to.

TYPE vs INSTANCE (sl-s2oa): a step definition's `(type :web)` marker
names the verb vocabulary it belongs to. Your `shiftlefter.edn`
:interfaces map declares named INSTANCES of these types; every
instance of a type gets this full vocabulary. A step targets an
instance with a leading `[name]` annotation (e.g. `[:admin-console]`);
unannotated steps default to the type-named instance when several
exist. The annotation names an instance, never a type or an adapter.

FRAMES ARE SCHEMA, NOT STEPS. A frame like `S navigates to O` names an
argument shape — writing it in a feature file will NOT bind. The only
step text this reference quotes is the `bind with:` example under each
frame; every one of those is machine-verified to bind. Copy those.
